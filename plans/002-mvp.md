# Plan 2 — MVP: the Discord → GitHub issue agent

The proving ground. I've built this bot twice with other frameworks; both times it took stupidly long. The framework earns its existence when this is a config file.

## User story

A team of 3–5 people constantly needs GitHub issues created. Instead of context-switching to GitHub:

1. Someone posts in the shared `#issues` Discord channel: *"the CSV export breaks on files over 10MB, probably the streaming parser — medium priority"*
2. The agent reads it, creates a well-formed GitHub issue (title, body, labels).
3. It replies in the channel with the issue link.
4. Everyone moves on. Fire-and-forget.

It can also handle other issue-management asks in the same channel: *"close #42"*, *"add the bug label to #17"*, *"what's open on the exporter?"*.

## One interaction

```
teammate                discord trigger          agent (inner loop)         github mcp
   │  message in #issues     │                          │                       │
   ├─────────────────────────►                          │                       │
   │                         ├── AgentEvent ───────────►│                       │
   │                         │                          ├── create_issue ──────►│
   │                         │                          │◄──── issue #123 ──────┤
   │                         │◄── result (link) ────────┤                       │
   │◄── reply: "Created:     │                          │                       │
   │    github.com/...123"   │                          │                       │
```

## The config

The entire implementation, target state:

```yaml
nickname: issue-bot        # the agent chooses its own name on first boot (Plan 1)
description: Turns team Discord messages into GitHub issues.

model:
  provider: anthropic
  id: claude-sonnet-5

purpose: |
  You manage GitHub issues for the acme/product repo.
  When someone describes work or a bug, create an issue with a clear,
  searchable title and a body that captures everything they said.
  Apply labels when obvious. Reply with only the issue link and a
  one-line summary. For other issue-management requests (close, label,
  query), do them and confirm briefly. If a message isn't an issue
  request, stay silent.

triggers:
  - type: discord
    channels: ["issues"]

tools:
  mcp:
    - name: github
      command: ["docker", "run", "-i", "ghcr.io/github/github-mcp-server"]
      env:
        GITHUB_TOKEN: ${GITHUB_TOKEN}

permissions:
  net: [discord.com, gateway.discord.gg, api.github.com]

memory:
  scope: thread

limits:
  max_steps: 10
```

Deployment: `docker run -v ./agent.yaml:/agent/agent.yaml --env-file .env looped/agent`

### Two implementation paths for the GitHub side

1. **MCP path** (config above): the GitHub MCP server as a sidecar process. Zero image customization, but a second process and ~40 tool schemas of context unless filtered.
2. **Skill path** (likely better — more minimal, cheaper on context, one process):

```yaml
skills:
  - ./skills/gh-issues.md      # teaches the gh CLI
permissions:
  net: [discord.com, gateway.discord.gg, api.github.com]
  run: [gh]
env:
  GITHUB_TOKEN: ${GITHUB_TOKEN}   # scoped to gh, never in model context
```

with a one-line custom image: `FROM looped/agent` + `RUN apk add --no-cache github-cli`. This exercises the "custom image provides the binary, skill provides the knowledge, permissions provide the safety" recipe from Plan 1. Build the MVP with the skill path; keep the MCP path as the documented alternative — both must work.

## What this MVP forces the framework to have

| Framework feature | Forced by |
|---|---|
| Outer loop / long-running service | Bot must sit on the Discord gateway 24/7 |
| Discord trigger + reply channel | Reading messages, replying in-channel |
| Inner agent loop with tool use | Deciding create vs. close vs. label vs. query |
| MCP client | GitHub tools come from the GitHub MCP server |
| Permissions v0 | Net allowlist; agent can reach GitHub/Discord and nothing else |
| Memory (thread scope) | Follow-ups like "actually make that high priority" |
| Config loader + schema | The YAML above must round-trip into a running agent |
| Docker packaging | The one-line `docker run` deployment story |

Deliberately *not* forced (and therefore not blocking): cron/webhook triggers, native `run_bash`, custom TS tools, multi-agent, compaction, CLI polish.

## Cut lines — what v1 of this agent does NOT do

- No slash commands or Discord UI components — plain messages only.
- No multi-repo routing — one repo, hardcoded in the prompt.
- No approval step — it creates the issue immediately (fire-and-forget is the point).
- No duplicate detection beyond what the model does naturally with its tools.
- No DMs — one shared channel.

## Done means

A teammate with no context can post a feature request in `#issues` and get a correct GitHub issue link back within seconds, from an agent whose entire definition is the YAML above, running in one container on the Mac mini.

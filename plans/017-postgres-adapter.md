# Plan 17 — Postgres: a second engine behind one interface

Looped's mono repo (`github.com/loopedautomation/mono`) wants to retire its own AI SDK integration and put a single Looped AF agent behind its chat product instead. That agent is not a solo operator's Discord bot; it answers for every app user in a product that already runs on Postgres. Two different asks hide inside that one sentence, and they have to be separated before either can be designed:

1. **Storage engine.** Can the framework's store write to Postgres instead of (or alongside) SQLite?
2. **Tenancy.** One agent process is now answering for many app users at once — how is their data kept apart?

The rough draft conflated these as one decision ("make SQLite the default, but Postgres as an adapter"). They're not the same problem and don't need the same answer at the same time: engine choice is a storage-layer refactor with a clean interface boundary; tenancy is a scoping concern that sits on top of whichever engine is underneath, and the framework already has half of a scoping key (`conversationKey`) to build on. This plan argues the engine question first, because it's the one the mono-repo integration cannot proceed without, and treats tenancy as the section that follows from it rather than a parallel track.

## What's actually true about the store today

The framework's stated design is "SQLite on a mounted volume — the canonical store" (`plans/001-architecture.md:85`), and the code matches that sentence exactly, not loosely:

- `Store` (`packages/core/store/store.ts:115`) is a concrete class wrapping `node:sqlite`'s `DatabaseSync` (`store.ts:1`, constructed at `store.ts:122`). Every one of its ~25 public methods — `sessionFor`, `saveMessages`, `appendMessages`, `loadMessages`, `recordRun`, `openRun`/`closeRun`, `recordAudit`, `createSchedule`/`listSchedules`, `rememberMemory`/`recallMemory`, `claimEvent`/`releaseEvent`, `getChannelState`/`setChannelState` — is synchronous, because `DatabaseSync` is synchronous.
- One SQLite file per agent, path `${dataDir}/${config.handle}.db` (`packages/core/runtime/service.ts:210`), `dataDir` from `AF_DATA_DIR` or `.looped` (`service.ts:208`). The Dockerfile mounts this as `VOLUME /data` (`images/agent/Dockerfile:34`) and docs describe it as "each agent owns one SQLite file" (`docs/docker-run.md:82`).
- Migrations are hand-rolled against SQLite specifically: schema version tracked via `PRAGMA user_version` (`migrations.ts:207-241`, `PRAGMA user_version` has no Postgres equivalent), `AUTOINCREMENT` primary keys, `INSERT OR IGNORE`, `datetime('now')` defaults, and — because SQLite can't `ALTER TABLE` past adding a column — two migrations (`002_archivable_sessions`, `004_open_runs`) that rebuild the whole table under `PRAGMA foreign_keys = OFF` (`migrations.ts:77-96`, `126-153`). None of that machinery ports.
- `sessions.conversation_key` is the only scoping key anywhere in the schema (`migrations.ts:27`). There is no tenant, account, or user column on any table. The design doc says why in plain language: "there is no mechanism for one agent to read another's memories" (`docs/memory.md:76`) — the framework's whole story for keeping data apart between agents is *one file per agent*, not a column inside a shared file.
- Six non-test files call store methods at all: `runtime/service.ts`, `runtime/status.ts`, `runtime/identity.ts`, `tools/memory.ts`, `tools/schedule.ts`, `eval/eval.ts`. That's a small, enumerable blast radius for whatever the interface change turns out to be.

That last point matters for scoping this plan honestly: this is not a sprawling refactor. It's a deep but narrow one.

## The seam that looks like it exists, but doesn't

`AgentServiceOptions` already has `store?: Store` (`service.ts:131`), which reads like dependency injection — pass your own store, get your own backend. It isn't one. `Store` declares private fields with `#db` and `#redactor` (`store.ts:116-117`), and TypeScript treats classes with ECMAScript private fields as *nominally* typed: only `Store` itself (or a subclass) is assignable to the type `Store`. A hand-written `PostgresStore` with an identical public method surface does not satisfy `store?: Store` today — the option exists for tests to swap in a `:memory:`-backed `Store` (`tools/memory_test.ts:6`, `runtime/identity_test.ts:36`, `eval/eval.ts:150`), not for swapping backends.

The framework has already solved this exact problem once, for a different subsystem, and the solution is worth copying rather than reinventing: `Provider` is a real interface (`packages/core/providers/types.ts:86`), implemented independently by `AnthropicProvider`, `OpenAICompatibleProvider`, `GeminiProvider`, and `CodexProvider`, selected by config through `createProvider()` (`providers/mod.ts:27`). Nobody asks "is SQLite the provider abstraction" for models — there's a real interface, several real implementations, and a factory. The store needs the same shape: extract an interface (name TBD — `Store` if the concrete SQLite class gets renamed to `SqliteStore`, or a fresh name if `Store` stays as a public type elsewhere), implement it twice, select the implementation from config the same way `model.provider` already does.

## The fault line is sync vs. async, not SQL vs. SQL

Extracting an interface is the easy 20% of this. The hard part is that `DatabaseSync` is synchronous by design, and no legitimate Postgres client is: `deno-postgres`, `postgres.js`, and `node-postgres` are all network I/O and therefore Promise-based. That means the interface can't just be "the same methods, implemented against a different engine" — every method has to return a `Promise`, because the Postgres implementation has no choice and the interface has to describe both implementations honestly.

That ripples exactly as far as the six call sites above, and it's mechanical rather than clever: `service.ts:478-479` (`sessionFor` then `loadMessages` before a run), `:493`/`:534` (`saveMessages` after compaction), `:657`, `:696`, `:719-720`, `:791` (the `appendMessages` callback passed into the loop mid-run), `:813` (final `saveMessages`) all need `await`. Same for `identity.ts:112,143`, `memory.ts:46,58,70,85`, `schedule.ts:86,108,122,134-135`, and whatever `status.ts` exposes over HTTP (`status.ts:53,70,75`, already async-friendly since it's inside `Response.json` handlers). None of this is architecturally risky — it's `deno task check` catching every missed `await` — but it is real, non-optional work, not a config flag. Anyone estimating this as "add a driver" is estimating the 20%.

One knock-on effect worth flagging early: `saveMessages`'s delete-then-reinsert-in-a-transaction pattern (`store.ts:169-183`) is the mechanism `plans/013-concurrency.md:39` leans on to make per-conversation serialization safe — "the full-replace `saveMessages` stays as is: per-conversation serialization is what makes it safe." That argument doesn't depend on SQLite specifically (Postgres transactions give the same guarantee), but it does depend on the *serialization*, which `013-concurrency.md`'s per-conversation FIFO provides regardless of engine. Nothing here contradicts that plan; it's worth a cross-reference once this lands so `013` doesn't read as SQLite-specific by accident.

## Default stays SQLite; Postgres is additive, not a replacement

The rough draft's proposed default — SQLite unless the operator configures otherwise — is right, and for a sharper reason than "don't disrupt existing users": self-hosted, one-container, one-job agents are the framework's primary shape (`plans/001-architecture.md:158`, "one agent per container"), and for that shape a mounted volume with zero external dependencies is strictly better than requiring a reachable Postgres server. SQLite is not the legacy option here; it's the correct option for the common case, and Postgres is the correct option for exactly one case: an agent that must share infrastructure with a system that already has its database opinions made, which is precisely the mono-repo situation. Config should read that way — `store.driver: sqlite | postgres` (or nested under a `store:` block; `sqlite` implicit today, explicit once a second option exists), `postgres.connection_env` resolved through the existing secret-reference convention (`api_key_env`-style, never a literal in YAML). No auto-detection, no "postgres if `DATABASE_URL` is set" magic — the operator states the engine the way they state the model provider.

## Tenancy: the part the rough draft actually wanted an answer to

The engine swap makes shared infrastructure possible; it says nothing about keeping one app user's conversation out of another's context. That's a schema and query-scoping question, and it exists independent of engine — a single shared *SQLite* file would have the identical problem if the mono repo pointed many app users at one agent process today.

Two shapes are available, and they're worth stating as a real choice rather than assuming the second:

- **One tenant column.** Every table that currently keys off `conversation_key` alone gains a `tenant_id` (or `account_id`) column, every store method takes a tenant argument, every query filters on it. `sessionFor`, `loadMessages`, `saveMessages`, memory, schedules, audit — all of them, since a memory or a schedule leaking across tenants is exactly as bad as a transcript leaking. This is more schema churn but it's one database, one connection pool, one place to look, and it's the shape Postgres is good at (row-level security is even available as a second line of defense once the column exists).
- **One database (or schema) per tenant, same code.** Keeps every existing query untouched — `conversation_key` stays the only key *within* a tenant's namespace — at the cost of a connection-routing layer that picks the right database before any store method runs, and Postgres connection-per-tenant at real scale eventually wants pooling (PgBouncer or similar) that SQLite's one-file model never had to think about.

The framework's existing bias points at the second shape without saying so: "one agent, one job" and "no mechanism for one agent to read another's memories" (`docs/memory.md:76`) is already a hard-isolation philosophy, just drawn at the container boundary instead of the tenant boundary. Moving that same line one level down — one *logical* store per tenant, addressed by a tenant id resolved from the trigger's conversation identity — is more consistent with what the framework already believes than bolting a `WHERE tenant_id = ?` onto a design that was never reviewed with multi-tenant leakage in mind. It also means the interface extraction above should carry a tenant/scope argument from the start even though SQLite's implementation ignores it (one file *is* the tenant boundary there), rather than retrofitting it once Postgres exists.

Either way, this is squarely a chat-trigger problem: the mono repo's agent needs a `chat` trigger surfacing per-app-user sessions, which `plans/001-architecture.md:59` already names as a "later" trigger blocked on exactly this kind of platform work ("Needed for dogfooding the framework inside Looped's product," `plans/005-platform.md:5`). This plan and that trigger are two halves of the same feature; neither is complete without the other, and the tenant-scoping decision belongs in whichever lands first since it constrains the other's interface.

## Latency: real, but not where the rough draft feared

The concern in the draft — "data flowing from the agent to a database set out as an adapter" — reads as if the risk is the network hop itself. It's smaller than that in practice: within a run, the store is touched at most a few times (load history once, append during tool calls if streaming persistence is on, save once at the end — see the call sites above), not per-token or per-tool-call in the hot path. A same-region Postgres connection adds single-digit milliseconds per round trip against a run that's already spending seconds to tens of seconds in model latency; it's noise relative to the LLM call, not a new bottleneck.

The real latency-shaped risk is connection setup, not connection use: SQLite has no connection to establish, so today's cold-start cost is zero. A pooled Postgres connection (via a pool the store owns, not one connection per run) keeps steady-state cost low, but the pool itself is new failure surface — a Postgres outage or network partition turns every run into a failure instead of every run into a slightly-stale-but-working file read, which SQLite-on-a-local-volume structurally can't experience the same way. Retry/backoff on the store's connection, and a clear typed error distinct from `ProviderError` for "store unavailable," should exist before this ships, not as a follow-up.

## Phasing

1. **Extract the interface.** Rename the SQLite class internally if needed, define the store interface with async signatures throughout, update the six call sites with `await`, no behavior change yet — this phase is done when `SqliteStore` implements the new interface and every existing test still passes unmodified in intent.
2. **Migrations, twice.** Design a schema-version table that isn't `PRAGMA user_version` (works on both engines, or is engine-specific with a shared `Migration` shape) and port the six existing migrations' *intent* to Postgres DDL (serial/identity columns instead of `AUTOINCREMENT`, native `ALTER TABLE` instead of the rebuild dance, `now()` instead of `datetime('now')`). This phase has no tenancy decisions in it yet — single-tenant Postgres, functionally equivalent to today's SQLite file.
3. **`PostgresStore`.** Implement the interface against a real driver, connection pool, retry/typed-unavailable-error, config surface (`store.driver`, `postgres.connection_env`), docs update to `docs/docker-run.md`'s persistence section so it stops asserting "each agent owns one SQLite file" unconditionally.
4. **Tenancy.** Whichever shape is chosen above, scoped to what the mono-repo chat trigger actually needs — this is likely co-designed with the `chat` trigger from `plans/001-architecture.md:59` rather than built ahead of it speculatively.

## Open questions

- **Interface name and boundary.** Does `Store` become the interface and the SQLite class becomes `SqliteStore`, or does the interface get a new name to avoid a rename touching six files' imports for no functional reason? Leaning toward keeping `Store` as the interface name — matches `Provider`'s pattern where the interface, not an implementation, owns the common name.
- **One tenant column vs. one store per tenant** — argued above as leaning toward per-tenant stores for consistency with the framework's existing isolation philosophy, but per-tenant Postgres databases at real app-user scale (hundreds to thousands of tenants) means either schemas-not-databases or a pooling layer that doesn't exist yet. Someone should hold this opinion against the mono repo's actual expected tenant count before committing.
- **Does SQLite deserve the same tenant argument threaded through its interface even though it never uses it**, for interface symmetry — or is that exactly the kind of speculative generality the codebase's own principles warn against? Leans toward yes, once, at interface-design time, rather than retrofitting every method signature when Postgres lands.
- **Which migration-version mechanism replaces `PRAGMA user_version`** for a Postgres backend — a `schema_migrations` table is the standard answer, but does SQLite move to the same table (dropping the pragma) for one shared code path, or does each engine keep its native mechanism behind the `Migration` interface?
- **Does the mono repo need `saveMessages`'s full-replace semantics at all**, or does a shared, high-traffic Postgres deployment want append-only history with a separate compaction step from day one, rather than inheriting a pattern that `013-concurrency.md` justified for a single SQLite writer?
- **Connection lifecycle**: one pool per `Store` instance (today's one-`Store`-per-agent-process model, unchanged), or does the mono repo's "one agent, many users" shape argue for a differently-scoped pool? Probably the former — the agent is still one process — but worth stating rather than assuming.
- **Should this block on the `chat` trigger, or can Postgres support ship for cron/webhook-triggered agents first** and the mono-repo chat integration follow once tenancy is designed? Shipping phases 1–3 without phase 4 gives any operator who wants Postgres for a single-tenant agent (e.g. sharing a Postgres instance for ops reasons, no multi-tenancy involved) a real, useful, smaller release.
